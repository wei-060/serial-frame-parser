# 串口数据帧解析器 (Serial Frame Parser)

纯 C 实现的串口数据帧解析器，专门处理真实串口场景下的**粘包、断包、噪声、坏帧**问题。

不需要任何硬件，在 PC 上直接编译运行。**23 个测试用例全部通过。**

---

## 一、要解决什么问题

串口收数据不像读文件 —— 它是一团**没有边界的字节流**，而且：

| 麻烦 | 说明 |
|---|---|
| **粘包** | 两帧首尾相连，中间没有任何间隔 |
| **断包** | 一帧只来了一半，另一半要等下一次 |
| **噪声** | 前后混着无关字节 |
| **假帧头** | 数据段里碰巧出现 `AA 55`，看着像帧头其实不是 |

解析器的任务就是**从这团乱麻里，把真正的帧一个不落地挖出来**，同时把假的一个都不放进来。

---

## 二、帧格式

```
+--------+--------+--------+--------+----------+---------+
| 帧头   | 地址   | 功能码 | 长度 N | 数据     | CRC16   |
| AA 55  | 1 字节 | 1 字节 | 1 字节 | N 字节   | 2 字节  |
+--------+--------+--------+--------+----------+---------+
          └─────────── CRC 计算范围 ───────────┘
```

- **整帧长度 = 7 + N**
- **CRC 计算范围**：地址 → 数据段最后一位（**不含帧头**、**不含 CRC 本身**）
- **CRC 存放顺序**：低字节在前（小端）
- **CRC 算法**：CRC16-Modbus（多项式 `0xA001`，初值 `0xFFFF`，逐字节右移 8 次）

---

## 三、三个关键设计

### 1. 帧头只是「候选」，CRC 才是「判决」

看到 `AA 55` **不能**认定这是帧头 —— 因为数据段里也可能出现 `AA 55`。

唯一可信的判据是：**按长度读完一整帧后，CRC 能不能对上。**

对不上，说明帧头找错了，此时**只能前进 1 格**重新找。
（不能按错误帧头后面的"长度字段"跳 —— 那是垃圾值，会把后面的真帧一起吞掉。）

### 2. 流式处理：不能把「扫过的字节」都丢掉

这是本项目最容易踩的坑。

如果字节流末尾**孤零零一个 `0xAA`**，它可能是下一帧帧头的前一半
（配对的 `0x55` 还没到）。所以这个字节**必须留着**，不能当垃圾丢掉。

> **批处理（一次性拿到整段）和流式处理的语义差别，就在这里。**
> 这是"能跑的代码"和"只在测试里能跑的代码"的分界线。

### 3. 与硬件解耦的结构

```
串口中断（ISR）：收到一个字节 → rxbuf_feed()          快，只做最轻的活
主循环（main） ：有空就调 rxbuf_take_frames()          耗时的解析放这里
```

**中断里只往缓冲区扔字节，解析全部放主循环。** 这是嵌入式的标准做法，
对应 STM32 上"串口中断 / DMA + 环形缓冲区"的经典结构。

## 四、编译运行

```bash
gcc *.c -o frame_parser.exe -std=c99
./frame_parser.exe
```

Windows 下双击 `build_run.bat` 即可（脚本会自动编译并运行）。

**依赖**：只用标准库；`<windows.h>` 仅在 Windows 上用于把控制台切到 UTF-8，
不涉及任何平台相关的业务逻辑。

## 五、测试

**23 个用例全部通过：**

```
第 1 步：CRC16 校验            4/4
第 2 步：解析完整帧            5/5
第 3 步：从字节流中提取帧      7/7
第 4 步：逐字节喂入            8/8
```

覆盖的场景：

| 场景 | 期望结果 |
|---|---|
| 单个合法帧 | 1 帧 |
| 两个帧粘在一起（粘包） | 2 帧 |
| 只来了半截（断包） | 0 帧，字节原样保留 |
| 3 个噪声 + 1 帧 + 2 个噪声 | 1 帧 |
| 坏帧 + 好帧 | **只提取出 1 帧**（坏的要丢，但不能吞掉后面的好帧） |
| 数据段里含 `AA 55` | 1 帧（**不能误判**） |
| `AA AA 55` 开头 | 1 帧（不能漏掉第二个 `AA`） |
| 帧头错（`12 34` / `AA 99` 两种形态） | 直接拒绝，返回 0 |
| 一帧被拆成两次到货 | 第一次 0 帧，第二次拼出 1 帧 |
| 灌入超过缓冲区容量 | 不越界，安全丢弃 |

> 其中"**坏帧 + 好帧**"和"**数据段含 `AA 55`**"两条，
> 是区分玩具代码和可用代码的关键。

**CRC 期望值的可信度**：所有测试向量都用**独立实现的 Python 版本**交叉验证过，
并包含 CRC16-Modbus 的**国际标准测试值**（`"123456789"` → `0x4B37`）。

## 六、代码结构

```
.
├── crc16.h / crc16.c      CRC16-Modbus 校验（独立模块，可复用）
├── frame.h / frame.c      帧结构定义、单帧解析、字节流分帧
├── ringbuf.h / ringbuf.c  接收缓冲区，支持逐字节喂入
├── main.c                 测试台（23 个用例）+ 程序入口
├── build_run.bat          Windows 一键编译运行
└── README.md
```

**模块之间的依赖是单向的**，没有循环引用：

```
main.c  →  ringbuf  →  frame  →  crc16
```

## 八、怎么移植到 STM32

这个解析器的设计目标就是**直接搬到单片机上用**：

1. `crc16.c` / `frame.c` / `ringbuf.c` **零改动**直接加进工程
2. 删掉 `main.c`（那是 PC 上的测试台）
3. 在串口中断里调 `rxbuf_feed()`
4. 在 `main` 循环里调 `rxbuf_take_frames()`

唯一要注意的是缓冲区大小的内存开销：
`RXBUF_SIZE` 改成适合你芯片的值即可。
